《无声有译》线上网站建设方案
================================================
版本：v1（2026-11-05）
定位一句话：把手语翻译从"电脑+ESP32屏"搬进浏览器，
任何人、任何设备，打开网址就能用。

================================================
一、为什么要上网站（现状对比）
================================================
现在这套：要跑 1.py（Python 环境 + 摄像头 + 训练好的模型），
屏幕那头还得接 ESP32。演示可以，日常用门槛太高。

上了网站之后：
- 使用者什么都不用装，开浏览器就行（手机浏览器也行）
- 不依赖你那台电脑，随时可用
- 对比赛/展示来说：发个链接，评委自己就能体验
- ESP32 那套不废弃——它是"硬件版"，网站是"线上版"，两条腿

================================================
二、给谁用，解决什么
================================================
场景一（主场景）：面对面沟通
  聋人朋友打手语 → 屏幕实时出词、拼句 → 对方直接看
  对方说话 → 网页实时出字幕 → 聋人朋友看
场景二（二期再做）：异地沟通
  两个人各开一个网页，进同一个"房间"，互相看到对方的文字

================================================
三、网站长什么样（页面规划）
================================================
就两个页面，不贪多：

1. 首页（index.html）
   - 一段话介绍：这是什么、给谁用
   - 一个大按钮："开始使用"
   - （可选）演示视频位

2. 识别页（app.html，核心页面）
   布局参考现在 1.py 的画面，分三块：
   ┌─────────────────┬─────────────────┐
   │  摄像头画面       │  通道A 手语出词区  │
   │  （带21点连线      │  词一个一个往上拼  │
   │   就像现在那样）   │  回车=发送整句    │
   │                 ├─────────────────┤
   │                 │  通道B 语音字幕区  │
   └─────────────────┴─────────────────┘
   交互照搬 1.py 的按键习惯：
   - 比划 → 词自动往上拼
   - 回车 → 组句发送，句子进对话区
   - z 撤销最后一个词，c 清空当前句
   这套交互已经验证过了，不改，直接平移。

================================================
四、技术架构（核心决策：识别放浏览器本地）
================================================
关键思路：手语识别不放在服务器，放在每个人的浏览器里跑。

浏览器端（干的活最多）：
  摄像头 → MediaPipe Hands（JS版，官方有）
        → 提取 21×2 关键点
        → 复刻 1.py 的归一化（手腕当原点、手腕到中指根当尺子）
        → 126 维特征
        → kNN 分类（模型文件几十KB，随网页下发）
        → 防抖状态机（滑窗投票/换词连续领先/按帧缩放，逐行翻译成 JS）
        → 出词、拼接
  语音字幕：浏览器自带 Web Speech API（免费、零后端、支持中文）

服务器端（一期几乎不干活）：
  只放网页文件本身（静态托管），不参与识别
  好处：
  - 不用买 GPU 服务器，成本趋近于 0
  - 延迟低（视频不出浏览器）
  - 多少人同时用都行，互不影响

复用你现有的东西（资产清单）：
  - sign_model.npz 的模型数据 → 导出成 JSON 给网页用（写个导出脚本）
  - 1.py 的归一化/防抖/出词逻辑 → 逐行翻译成 JS，逻辑一行不改
  - 校园词组表（CAMPUS_PHRASES）→ 照搬
  - sentence_api 的组句 → 一期先用规则版（词组表+语序微调），够用
  - train_model.py 重训流程不变，重训完重跑导出脚本即可更新网页模型

================================================
五、分期计划
================================================
一期：网页版识别器（无后端，先做这个）
  产出：一个网页，开摄像头就能翻，面对面可用
  步骤：
    1. 导出脚本：npz 模型 → model.json
    2. 页面骨架：摄像头画面 + 出词区 + 字幕区
    3. JS 版识别管线：关键点→归一化→kNN→出词
    4. JS 版防抖状态机（最容易出错的环节，逐行对照 1.py 验证）
    5. 组句、发送、撤销/清空
    6. 联调：拿"我现在要去学校"等回归句子实测，对齐 1.py 的准确率
  部署：静态托管 + HTTPS（摄像头权限的硬要求）

二期：异地互通（加一个小服务器）
  产出：房间号机制，两人异地实时互看
  服务器只做 WebSocket 消息转发（Node.js 两百行以内）
  只传文字不传视频，学生机/免费层就够

三期（可选）：账号 + 云端历史
  注册登录、识别记录存云端、换设备回看
  到这一期才需要数据库/用户系统，可用托管后端现成方案

================================================
七、风险与对策
================================================
1. MediaPipe JS 首次加载约 10MB（CDN）
   → 有缓存；演示前提前打开一次
2. 浏览器识别精度是否和电脑端一致
   → 防抖参数照搬 1.py 已调好的值，联调时用同一批回归句子对比，
     不达标就逐参数对齐（这套排查流程我们熟）
3. Web Speech 字幕效果不确定
   → 先实测中文识别率；不行换百度流式（走自己服务器中转，二期顺手做）
4. 手机浏览器性能
   → 一期先保证电脑端，手机端实测后再说，不提前优化
